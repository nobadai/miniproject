# KoELECTRA 학습 안내

## 1. 문서 목적

이 문서는 보이스피싱 판정에 사용하는 KoELECTRA 분류 모델의 **현재 학습 로직**과 **재학습이 필요한 이유**, 그리고 **개선 방안**을 정리한다.

관련 파일은 다음과 같다.

| 파일 | 역할 |
| --- | --- |
| `backend/app/services/voice_phishing_model.py` | 입력 구성과 추론. 학습과 공유하는 기반 |
| `backend/app/services/train_voice_phishing.py` | 학습 실행 진입점 |
| `backend/resources/voice_phishing/evaluations/eval_v1.jsonl` | 학습 데이터 |
| `backend/artifacts/voice_phishing/koelectra/` | 학습 산출물. 서비스가 읽는 모델 |

## 2. 왜 재학습이 필요한가

실제 통화 영상(2분 49초, 법원 등기 사칭 → 가짜 조회 사이트 유도 → 중앙지검 사칭)을 업로드했을 때 **모델 점수가 0.130** 으로 나왔다. 정상 통화와 구분하지 못했다는 뜻이다.

같은 통화에 대한 다른 신호는 다음과 같았다.

| 신호 | 점수 |
| --- | --- |
| 규칙 점수 | 0.784 |
| 시퀀스 점수 | 0.650 |
| **KoELECTRA** | **0.130** |

규칙과 시퀀스는 위험을 잡아냈지만 모델만 반대 방향을 가리켰다. 이 상태로는 최종 판정이 `suspicious`까지 가지 못한다.

`decide_prediction`의 판정 조건을 보면 모델이 사실상 관문 역할을 한다.

```text
rule >= 0.75 and sequence >= 0.80   → suspicious
model >= 0.80                       → suspicious
model >= 0.70 and sequence >= 0.75  → suspicious
```

규칙만으로 `suspicious`를 내려면 시퀀스까지 0.80을 넘겨야 하므로, 실무에서는 **모델 점수가 낮으면 판정이 `unknown`에 머문다.** 규칙 사전을 아무리 보강해도 이 한계는 남는다.

모델이 왜 못 잡았는지는 학습 데이터 성능과 대조하면 분명해진다.

| 구분 | 모델 점수 |
| --- | --- |
| 학습셋 정상 23건 | 중앙값 0.058 (최대 0.121) |
| 학습셋 피싱 23건 | 중앙값 0.880 |
| **실제 업로드 통화** | **0.130** |

학습 데이터에서는 정상과 피싱을 거의 완벽하게 가른다. 그런데 처음 보는 실제 통화는 정상 쪽으로 분류했다. **학습 데이터에 없는 수법을 일반화하지 못하는 상태**다.

## 3. 모델의 역할

최종 점수는 세 신호의 가중합이다.

```text
fusion = 0.33 x 규칙 + 0.34 x KoELECTRA + 0.33 x 시퀀스
```

- **규칙**: `keywords.yaml` 사전의 부분 문자열 매칭. 설명 가능하지만 표현이 바뀌면 놓친다
- **시퀀스**: 발화 순서(신원제시 → 문제제기 → 격리요구 → 행위지시) 전이 분석
- **KoELECTRA**: 사전에 없는 우회 표현과 문맥을 담당

즉 모델은 **규칙이 놓치는 표현 변형을 잡으라고 넣은 구성 요소**다. 지금은 그 역할을 못 하고 있다.

## 4. 현재 학습 로직

### 4.1 데이터

`eval_v1.jsonl` 한 파일을 사용한다.

- 46건, `normal` 23 / `suspicious` 23으로 균형
- 발화 수 중앙값 34개 (최소 4, 최대 620)
- 형식: `{"call_id", "label", "turns": [{"idx", "speaker", "text"}]}`
- `speaker`는 `other`(상대) 또는 `self`(본인)

`load_training_rows()`가 라벨과 발화 존재 여부를 검증하고, 규격에 맞지 않으면 학습을 시작하지 않고 중단한다.

### 4.2 입력 구성

`encode_turns()`가 통화 하나를 모델 입력 청크 목록으로 바꾼다.

1. `format_call_text()` — 발화를 `[상대] 텍스트` / `[본인] 텍스트` 형태로 이어 붙인다. 화자 정보를 문자열에 남겨 모델이 누가 말했는지 볼 수 있게 한다
2. 토크나이저가 **최대 512 토큰, stride 128 겹침**으로 자른다. 겹침을 두는 이유는 청크 경계에서 문맥이 끊기는 것을 막기 위해서다
3. `choose_chunks()` — 청크가 **8개**를 넘으면 시작과 끝을 반드시 포함하도록 균등 간격으로 고른다. 긴 통화의 도입부(신원 사칭)와 마무리(행위 지시)를 모두 남기려는 선택이다

### 4.3 학습 루프

통화 전체에 라벨 하나만 붙어 있고 어느 발화가 근거인지는 표시되어 있지 않다. 그래서 **통화 단위 Top-K 방식**을 쓴다.

각 통화마다 다음을 반복한다.

1. `select_top_chunks()` — **현재 모델**로 모든 청크를 채점해 피싱 확률이 높은 **상위 3개**를 고른다 (`torch.no_grad`)
2. 고른 청크만 다시 forward해 **logits 평균**을 통화 단위 logits로 삼는다
3. 통화 라벨과 cross entropy loss를 계산하고 역전파한다

정상 통화 중에도 위험해 보이는 구간이 있고 피싱 통화에도 잡담 구간이 있다. 전체 청크를 평균 내면 신호가 희석되므로, **모델이 스스로 근거 구간을 고르게 하는 방식**이다.

추론(`KoElectraAnalyzer.score`)도 같은 Top-K 구조를 쓴다. `encode_turns()`와 `forward_chunks()`를 학습과 그대로 공유하므로 학습과 서비스의 입력 처리가 어긋나지 않는다.

### 4.4 하이퍼파라미터와 재현성

| 항목 | 기본값 |
| --- | --- |
| base model | `monologg/koelectra-base-v3-discriminator` |
| epochs | 2 |
| learning rate | 2e-5 (AdamW) |
| batch size | 2 |
| top-k | 3 |
| max length / stride | 512 / 128 |
| max chunks | 8 |
| seed | 42 |

`random`, `torch`, `cuda` 시드를 모두 고정하고 cuDNN을 결정적 모드로 둔다. 같은 데이터로 다시 돌리면 같은 모델이 나오게 하려는 설정이다.

Mixed Precision은 CUDA에서만 켠다. `GradScaler`는 `enabled=device.type == "cuda"`로 두어 CPU에서는 그대로 통과시킨다. GPU가 없어도 학습은 되지만 크게 느리다.

### 4.5 산출물

`artifacts/voice_phishing/koelectra/`에 `save_pretrained`로 저장한다. 모델 가중치가 약 450MB다. 서비스는 이 디렉터리를 읽으며, 없으면 `KoElectraAnalyzer` 생성 시 `FileNotFoundError`로 실패한다.

## 5. 현재 학습의 한계

### 5.1 검증 분할이 없다

`train_model()`은 입력 46건을 **전부 학습에 쓴다.** 학습에 쓰지 않은 데이터로 성능을 재는 절차가 없다.

따라서 `eval_v1.jsonl`로 측정한 수치는 전부 **학습 데이터 성능**이며, 실제 성능보다 낙관적이다. 2절에서 학습셋은 잘 가르는데 실제 통화는 못 잡은 결과가 이 격차를 보여준다.

### 5.2 데이터가 너무 적다

46건은 딥러닝 분류기 학습에 매우 적은 양이다. 수법 하나가 통째로 빠져도 알아차릴 방법이 없다. 실제로 **가짜 사이트 유도형이 학습셋에 0건**이었다.

### 5.3 학습 데이터와 실제 입력의 성격이 다르다

| | 학습 데이터 | 실제 서비스 입력 |
| --- | --- | --- |
| 발화 수 중앙값 | 34 | 40 이상 (실제 전사본은 중앙값 69) |
| 문장 형태 | 정리된 문어체 | STT 출력. 잘린 구어체, 오인식 |
| 화자 구분 | `other` / `self` 구분 있음 | **전부 `other`** |

특히 화자 구분이 다르다. 서비스는 화자 분리를 하지 않아 `WhisperTranscriptionClient`가 모든 발화를 `other`로 넣는다. 반면 학습 데이터에는 `self`가 섞여 있다. `format_call_text()`가 화자 태그를 문자열에 넣으므로, **학습 때 본 입력 형태와 서비스 입력 형태가 다르다.**

### 5.4 라벨이 2종뿐이다

모델은 `normal` / `suspicious`만 출력한다. 최종 판정에는 `unknown`이 있지만 모델은 이를 학습하지 않는다. 애매한 통화에 대한 모델의 불확실성이 점수에 제대로 반영되지 않는다.

## 6. 개선 방안

우선순위 순이다. 위쪽이 비용 대비 효과가 크다.

### 6.1 실제 전사본을 학습 데이터로 편입 (최우선)

`backend/resources/voice_phishing/transcripts/`에 **금융감독원 실제 통화 전사본 47건, 총 7,269 발화**가 이미 들어 있다. 발화 수 중앙값 69로 학습셋(34)보다 실제 서비스 입력에 가깝다.

`parse_transcript()`가 이 형식을 이미 표준 `turns`로 바꿔 준다. 라벨을 붙여 `eval_v1.jsonl` 형식으로 변환하면 학습 데이터를 **46건 → 90건 이상**으로 늘릴 수 있다.

주의할 점이 있다. 이 전사본은 **전부 피싱 사례**라 그대로 넣으면 클래스 불균형이 생긴다. 정상 통화 데이터를 함께 확보하거나 클래스 가중치를 줘야 한다.

미탐이 확인된 통화(가짜 사이트 유도형)는 반드시 포함한다. 같은 유형을 다시 놓치는지 확인할 수 있는 회귀 사례가 된다.

### 6.2 화자 표기를 서비스 입력에 맞춘다

서비스가 모든 발화를 `other`로 넣는 이상, 학습 데이터의 `self`/`other` 구분은 실제로 쓰이지 않는 정보다. 둘 중 하나를 택해야 한다.

- **학습 데이터를 서비스에 맞춘다** — 학습 시 화자 태그를 제거하거나 전부 `other`로 통일한다. 간단하고 즉시 격차가 사라진다
- **서비스를 학습 데이터에 맞춘다** — 화자 분리(diarization)를 도입한다. 정확도는 올라가지만 STT 파이프라인 변경이 필요하다

### 6.3 검증 분할을 도입한다

학습 성능이 아니라 **처음 보는 데이터 성능**을 재야 한다.

- 데이터가 적으므로 계층화 k-fold 교차검증이 적합하다
- 최소한 hold-out 분할이라도 두고, 학습에 쓰지 않은 건으로 지표를 계산한다
- 지표는 정확도뿐 아니라 **정상 통화 오탐률**을 함께 본다. 정상 통화를 피싱으로 잘못 알리는 비용이 크기 때문이다

### 6.4 학습량을 데이터에 맞춰 재조정한다

데이터를 늘린 뒤 epochs 2가 여전히 적절한지 다시 본다. 46건 기준으로 정해진 값이다. 6.3의 검증 분할이 있어야 과적합 여부를 판단할 수 있으므로 순서상 뒤에 둔다.

## 7. 학습 실행 방법

`backend/` 에서 실행한다. GPU가 있으면 자동으로 CUDA를 사용하고, 없으면 CPU로 내려가며 경고를 남긴다.

```bash
.venv/Scripts/python.exe -m app.services.train_voice_phishing
```

주요 인자는 다음과 같다.

```bash
.venv/Scripts/python.exe -m app.services.train_voice_phishing \
  --input resources/voice_phishing/evaluations/eval_v2.jsonl \
  --output artifacts/voice_phishing/koelectra \
  --epochs 3
```

| 인자 | 기본값 | 설명 |
| --- | --- | --- |
| `--input` | `eval_v1.jsonl` | 학습 JSONL |
| `--output` | `artifacts/voice_phishing/koelectra` | 저장 위치 |
| `--epochs` | 2 | 학습 반복 |
| `--learning-rate` | 2e-5 | |
| `--top-k` | 3 | 통화당 사용할 상위 청크 수 |
| `--seed` | 42 | 재현성 |

**기존 모델을 덮어쓰기 전에 백업한다.** 성능이 떨어지면 되돌릴 수단이 필요하다. `--output`을 새 경로로 지정해 비교한 뒤 교체하는 방식을 권장한다.

## 8. 재학습 후 필수 후속 조치

**저장된 분석 결과를 삭제해야 한다.** 같은 파일을 다시 업로드하면 Database에 저장된 이전 분석을 그대로 반환하므로, 모델을 바꿔도 옛 점수가 나온다.

```bash
docker compose exec -T database psql -U finance_ai -d finance_ai -c "DELETE FROM voice_phishing_analyses"
```

STT 전사 캐시(`backend/cache/transcripts/`)는 모델과 무관하므로 지우지 않아도 된다. 전사 결과는 그대로 재사용되어 재분석이 빠르다.

## 9. 주의사항

- 학습 데이터를 늘릴 때 **개인정보가 포함된 실제 통화**를 그대로 넣지 않는다. 기존 전사본처럼 마스킹된 자료를 사용한다
- `eval_v1.jsonl`을 학습과 평가에 동시에 쓰는 현재 구조에서는 성능 수치를 그대로 신뢰하면 안 된다. 6.3을 적용하기 전까지는 모든 지표에 이 전제를 함께 기록한다
- 규칙 사전(`keywords.yaml`)과 모델은 역할이 다르다. 사전은 정밀도, 모델은 재현율을 담당한다. 모델이 못 잡는다고 사전에 우회 표현을 계속 늘리면 정상 통화 오탐이 늘어난다
